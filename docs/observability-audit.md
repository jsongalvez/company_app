# Observability audit

Which signal would have caught each company_app bug sooner, and by how much. Read-only audit: no code changed.
Window: 64 feedback reports, 2026-10-18 to 2026-10-25, plus the non-feedback incidents in the second table.
Every claim carries a label: **checked** (read from the database, git, logs or a service this session), **inferred** (follows from checked facts), **guessed**.

> **Caveat (owner, 2026-10-25):** all 64 feedback reports came from the owner testing the app. Do not assume real users will report problems at all. Read G as "only the owner's own testing caught it", not as "a user report will catch it". For real users, automatic signals (B, C, E, F) are the only ones that fire.

**Reading.** 61 of 64 reports (95%, checked count of the table, inferred classification) are layout, wording, missing-feature or cache-staleness complaints. The server answered correctly and the page did not throw. No error tracker, trace id or alert could see them. They are found by the Feedback button and by browser tests at 375px.
The measurable gain from observability is on the deploy path (E), not the feedback path.

**Top 3 signals by bugs caught.**

1. **B, failed fetches and JS errors on the phone.** 3 feedback rows (13ddb174, c4570ade, ab98d6ce). Rows are checked; "would have caught" is inferred. The gain is the repro step, not time: users reported within minutes of the fault (inferred from the report timestamps, which sit minutes from the fix windows).
2. **A with D, trace id plus kept logs.** 2 rows. A alone is weak: `logs/app.log` on the app server starts at 2026-10-25 12:43 and holds 156 `request_completed` lines, so a trace id older than that restart points at nothing (checked).
3. **E, deploy-failure alert.** 1 event, the largest time gain. Coolify marked 14eb757b failed 01:14Z (09:14 PST) and a24c109b failed 23:54Z the day before (07:54 PST). The fix, 8bb5f234, landed at 13:24 PST: 5.5 h and 4.2 h later (checked from the Coolify record and commit time). The server stayed on 0b43ce6d the whole time (checked). The shortfall was noticed as "server behind master" earlier but the cause stayed unchecked until midday (inferred from the work record).

**Noise warning for B and C.** 28 of 64 reports carry a "Last refused request" line, 26 of them a 403, and 20 are the same `dashboard/today` 403 (checked, by query on `user_feedback.details`). That call is refused for people who are not staff, which is normal (inferred from the 4xx being constant across unrelated reports). A tracker that alerts on every 4xx would page on this call all day. Track 5xx, thrown errors and 4xx outside an allow-list only.

**Report to fix time.** For the 61 reports with a fix commit identified, median 50 min, p90 10 h, max 38 h (checked timestamps; the report-to-commit pairing is inferred from commit subjects, and two reports are paired with the commit that finished their feature).
Those times are already short. Earlier detection can only shorten the time before a user notices, and for these reports the user was the first to see the fault.

## Evidence behind the labels

- Reports and timestamps: `select` on `user_feedback`, 64 rows, 2026-10-18 to 2026-10-25 (checked).
- Fix commits: `git log` on master and `docs/patterns.md` (checked subjects, inferred pairing).
- Log retention: `logs/app.log` begins 2026-10-25 12:43, the last restart (checked). Older request lines are gone.
- Feedback has no trace id: `user_feedback` columns are id, user, kind, message, page, details, app_version, status, created_at (checked). `details` holds the screen size, browser and last refused request only.
- Trace ids exist in logs and in the `X-Trace-Id` response header (checked in an earlier code read, not re-read here).

## What this does not show

- Whether the 3 B rows would have been caught before the user noticed. Users reported within minutes (inferred), so the likely gain is faster diagnosis (guessed).
- Bugs no one reported. A tracker could surface those; this audit cannot count them (guessed: unknown).
- Whether the classification of 61 rows as G alone is too strict. A reader who finds a row a tracker would have caught should move it and the count.
