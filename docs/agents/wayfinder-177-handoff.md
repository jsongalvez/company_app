## The ntfy root-cause (user-flagged, prioritized — see Critical follow-ups)

The user asked to **prioritize ntfy notifications when an agent triggers a user decision** (Question tool, permission requests). The loop's `wayfinder-loop.sh` ALREADY has the mechanism — `pending_forms`/`pending_perms` → `notify "wayfinder needs you"` / `"wayfinder needs permission"` — but **it does not fire for short questions**. Root-caused live this session:

- **The filter is correct.** A live probe (throwaway session + background poll of `/api/session/<sid>/form` during a real question) captured the pending-form shape: `{"data":[{"id":"frm_...","metadata":{"kind":"question",...},"fields":[...]}]}` — `pending_forms`'s `.metadata.kind == "question"` match is right.
- **The bug is the polling structure.** `supervise_session` calls `wait_idle` (a blocking `POST /api/session/<sid>/wait` with a 180s timeout) and checks `pending_forms` ONLY after the wait returns. While a question is pending, the wait **blocks until the user answers** — a question asked and answered inside one wait slice is never observed. The user's test question this session was pending **~5 seconds** (probe t=2→t=3); no notification fired. Only a question that outlives a full 180s slice would fire — the exactly-wrong threshold for a responsive human.
- **The fix (next session)**: decouple form/permission detection from the blocking wait — restructure `supervise_session` to a short-tick poll loop (every ~5-10s: check `pending_forms`/`pending_perms` → notify-once each until answered; check `newest_unprocessed` for completion; keep the session_progress token-fingerprint for zombie detection). Any pending question then pings within seconds, even one answered in 5s. Also add a `log "notify: ..."` line to `notify()` (or at the fire sites) — the loop currently doesn't log notifications, so firing is invisible in `.wayfinder-loop.log` (this session could not tell from the log whether the ping fired; only the user's phone could). Do NOT touch the gitignored `.wayfinder-loop.env` topic value (`WAYFINDER_NTFY_TOPIC`, currently `wf-0w9uaukg` per the standing note).

## Patterns + learnings

- **A blocking-wait loop swallows short-lived state — verify the notification path fires, not just that it exists.** The loop "had" ntfy-on-question for many sessions; it had never fired for a responsive human. The root cause was structural: the check only runs after a 180s blocking wait, and `/wait` returns only when the answer lands. The session-level lesson for the review loops: a gate/notify that only runs at slice boundaries is effectively absent for short events. The live probe (background poll + a real question) is the pattern that proved it — reproduce the event, don't trust the code reading.
- **The notify() function's silence is a truth-class gap.** The loop logs spawns/transitions but not notifications — so whether the human was pinged is invisible in `.wayfinder-loop.log`; only the phone knows. Any loop-side notification work should log the fire (and ideally the reason).
- **The jargon-first question cost a round-trip.** My first decision pitch was dense with handler/family/keep-last vocabulary; the human answered `/wait-what`. The plain re-pitch ("throw away old failures the way old data is already thrown away; it affects only the Notifications and Relief screens") landed immediately. The decision-loop's L5 comprehension lens is not a nice-to-have — it is the human-facing surface of the whole exchange, and the standing frame ("simple language, gist at a glance") should be re-read before every human question.
- **Prior-session patterns unchanged:** claim-first, facts-via-code, one-ticket-per-session, commit local not pushed, gate green before commit, the phased loop until 0 HARD, diff-verified map edits, sub-issue-API-404 → `Part of #<map>` fallback.
- **New test-verification pattern (this session):** the throwaway-session + background-`/form`-poll probe is a reusable way to capture opencode API shapes live (see the ntfy root-cause).
