## Patterns + learnings (cumulative)

- **Session-62 additions**:
  - **Fog-line markers must be read literally — a "marker" site of the right SHAPE but wrong FAMILY doesn't fire the graduation.** The update-one fog said "watch for a second site that writes 'update the row matching id'" — FinanceReportsViewModel:1053/1158 literally write `map { if (it.id == updated.id) updated else it }`, but they're raw `MutableStateFlow` writes (no KeepLast mirror/freshest/`mutate` discipline, `.orEmpty()` fallback, always-write), they predate the #164 P5 (which counted "one adapter" with them in view), and the fog's seam is explicitly "on the KeepLast family". The marker is a NEW KeepLast-family adapter; raw-flow sites of the same map-if shape don't count. Take the next-priority fog line instead — don't force a graduation on a shape-match.
  - **P5 can reshape the spec's fix-shape — the loop-back re-verifies it.** The fog named `checkpoint`/`isCurrent`/`fallback`; P5a collapsed the pair into `stamp: () -> Long` (read-twice semantics). This is a legitimate in-ticket ARCH fix IF the loop-back pass confirms spec intent (concentration, behavior-preservation, stale-never-deserialized) survives the reshape — it did, and the collapse dissolved a two-sighted SOFT (guard-wiring duplication) as a bonus. Record the deviation loudly in the resolution, don't bury it.
  - **At-fallback-time state reads must name the mirror, not the state.** When a stale landing commits the fallback, the landing's OWN Loading write (handler sets it at coroutine start) is current — so `freshestValue()` resolves to `_freshest`, not `state as? Success`. Comments that say "reads the exact Success" are wrong by one indirection; the freshest mirror is exact on Main.immediate, but say that.
  - **Test staleness premises must be structural, not timing-dependent.** The non-success test's "bump the stamp so the landing would be stale" raced the real-IO 500 thread (a non-2xx completes off the test scheduler — the #93 idiom) — if the 500 landed first the "stale" premise silently vanished. A counter stamp (`stamp = { reads++ }`: capture 0, landing 1) makes the disagreement structural regardless of scheduling.
- Prior-session patterns unchanged: claim first, facts-via-code, one-ticket-per-session, resolution → close → map update → handoff, batch-fix commits per pass, `git diff <last-pass-commit>` per pass, **grep-verify every batch fix before committing** (no fix-that-didn't-land this session), **check the review window for runner daemon commits** (clean this session — ticket window was exactly the 4 ticket commits), **truth-class rewords checked against the code's firing conditions** (this session's variant: the error() message's reachability — a message can name the wrong missing piece even when it's never fired in production).
