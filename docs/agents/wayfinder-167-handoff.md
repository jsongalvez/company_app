## Patterns + learnings (cumulative)

- **Session-64 additions**:
  - **"Verify the fog count" is now two-way.** Session 63's lesson was "stale counts are claims to falsify" (the #162 P5 undercounted). Session 64's count was RIGHT — but the discipline still earned its keep: the verification surfaced the `_exportErrors` near-miss, and the ticket documented WHY it's a different family (state-probe coalescer, not an InFlightGuard). Verifying a correct count is not wasted — the exclusion reasoning is what P1/P2 judged the spec against. The discipline is "verify and document either way", not "assume stale".
  - **A rejected-begin path can be structurally unreachable through the public API — and that's a proof, not a coverage gap.** The invariant "error(key) ⇔ marker(key) mutually exclusive by construction" (fail finishes before setting; begin clears after arming) makes the "rejected begin retains the stale error" branch untestable AND unviolable. When P5b flagged it as a coverage gap, the proof (all 4 phases × 3 passes agreed, P5a confirmed buried) killed the finding — a test for it would be unfalsifiable. Distinguish "unreachable but real" from "structurally impossible".
  - **P5's deletion test caught a double-duty `clear()` at the design level.** `clear()` (guard+errors) served two semantic callers: FinanceReports' superseded-escape (markers MUST die) and UserVM's reload (markers provably empty, errors only). The second caller rode an external invariant with a 4-line hazard comment. `clearErrors()` (errors-only) deleted the invariant-ride — one-line, behavior-identical, no complexity moved. When a method's callers disagree about what it should clear, split the primitive instead of documenting the ride.
  - **When a VM port changes error-then-finish to finish-then-error, the order swap is unobservable** (two separate StateFlows, same synchronous frame, conflation before any recomposition) — but ONLY when both are frame-local synchronous writes. State it once in the ticket; P2/P4 both re-derived it independently.
- Prior-session patterns unchanged: claim first, facts-via-code, one-ticket-per-session, resolution → close → map update → handoff, batch-fix commits per pass, `git diff <last-pass-commit>` per pass, **grep-verify every batch fix before committing**, **check the review window for runner daemon commits and re-scope to the ticket commits** (fired this session — `8f20d64`), truth-class rewords checked against the code's firing conditions.
