## Patterns + learnings

- **A blocking-wait loop swallows short-lived state — fix it by polling, not by shrinking the wait.** The #177 root cause was structural (checks ran only after a 180s wait); shrinking the timeout to 30s would have narrowed but never closed the window. The tick loop (5s) closed it: any pending question is observed within one tick regardless of how long it lives. Confirmed the #177 session-level lesson for the review loops: a gate that only runs at slice boundaries is effectively absent for short events.
- **The `notify()` log line closes a truth-class gap.** Before: `.wayfinder-loop.log` had no record of notification fires — the phone was the only witness. After: every fire is a `notify: <title> — <body>` line, and the answered/permission-granted transitions log too. The live test could be read from the log alone (23:34:28 fire, 23:34:48 answered) — the phone confirmation was corroboration, not the only evidence.
- **The restructure surfaced a second latent bug by changing the completion path.** The old `return 0` after spawn was load-bearing in a way nobody had noticed: it silently dropped the freshly spawned session from supervision (5h window in the old log). The new `continue` with tick-state reset is the one-line fix that makes the chain self-supervising. Lesson: when a control-flow refactor touches a "return to caller" path, trace what the caller does with control after — it may be an accidental boundary.
- **Harness-first before touching the live daemon.** The 14-assertion stub-`api()` harness ran the shipped function text before the daemon restart — the restart was then a formality, and the live test confirmed what the harness had already shown. This is the loop-infra analogue of the phased review's "negative control red" discipline.
- **Prior-session patterns unchanged:** claim-first, facts-via-code, one-ticket-per-session, commit local not pushed, gate green before commit, the phased loop until 0 HARD, diff-verified map edits, sub-issue-API-404 → `Part of #<map>` fallback.
