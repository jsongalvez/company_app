## Patterns + learnings (cumulative)

- **Session-63 additions**:
  - **Fog-line factual counts are claims to falsify, not instructions.** The #162 P5's "hand-rolled at 2 sites" was a count of the code at P5 time — AuditLogVM's `_acknowledgingIds` was the same shape and existed then; the P5 missed it. Verify the count in code before writing the ticket; if the count is stale, correct it loudly in the ticket body (the ticket is then the spec authority, and P1 judges against the ticket, not the fog). A unifier built to the fog's stale count would ship 75% of the intent with a fourth identical hand-roll left in place.
  - **When a port reorders two independent guards, prove outcome-equivalence by reasoning about the markers, not the line order.** UserVM's `runMutation` swapped the in-flight check and the Loading check. Both are pure-return predicates; the invariant is "the marker is added only when both guards pass" — preserved. State the invariant, don't just swap lines.
  - **A helper's return-value change can preserve an ordering constraint.** FinanceReports `beginAction` returning `tryBegin`'s Boolean keeps the error-clear gated on a successful begin — the old check-before-begin order survives as a return-check (`if (!beginAction(key)) return`). This is behavior-identical AND single-line-per-caller.
  - **KDoc dedup must point at the home of the rationale, not the member that references it.** Pass-2 caught `[InFlightGuard.tryBegin]` mispointing — the #143 rationale lives in the InFlightGuard CLASS KDoc, not the method KDoc. When deduping a rationale, cite the exact block that holds it.
  - **Cross-wire hazard documentation is a contract, not a guard behavior.** `clear()` + re-arm + a stale request's unconditional `finish` removing the newer marker is inherent to set-subtract coalescing; the protection is the ADOPTER's terminal-path gating (the generation guard). Document it as an adopter contract; don't try to make the guard defensive (a marker-identity-aware guard would need tokens — the #165 stamp lesson).
- Prior-session patterns unchanged: claim first, facts-via-code, one-ticket-per-session, resolution → close → map update → handoff, batch-fix commits per pass, `git diff <last-pass-commit>` per pass, **grep-verify every batch fix before committing**, **check the review window for runner daemon commits** (clean this session — ticket window was exactly the 3 ticket commits), **truth-class rewords checked against the code's firing conditions**.
