- **`mockEngine(handler: MockRequestHandler): HttpClientEngine` via `MockEngineConfig().apply { requestHandlers.add(handler); dispatcher = Dispatchers.Unconfined }`** (new this session, in `TestHelpers.kt:54-67`): the handler-based overload enables URL routing (handler receives `HttpRequestData`), request counting (test's `var requestCount = 0` closure mutated by lambda), and multi-response scenarios. Setting Unconfined makes `withContext(dispatcher + callContext) { handler(...) }` run inline on the calling thread (test thread = the testScheduler-driven Main thread), so no async IO roundtrip races the virtual-time drain. - **`runTest(testScheduler)` via TestCoroutineScheduler as CoroutineContext.Element** (new this session, in `NotificationBadgeViewModelTest.kt:63,81,107`): `kotlinx-coroutines-test 1.11.0`'s `runTest` signature is `public fun runTest(context: CoroutineContext = EmptyCoroutineContext, timeout: Duration = DEFAULT_TIMEOUT.getOrThrow(), testBody: suspend TestScope.() -> Unit): TestResult` — NO `testScheduler` named parameter (earlier version had it). `TestCoroutineScheduler` IS-A `CoroutineContext.Element` (`TestCoroutineScheduler.kt:26-30`: `public class TestCoroutineScheduler : AbstractCoroutineContextElement(TestCoroutineScheduler), CoroutineContext.Element { public companion object Key : CoroutineContext.Key<TestCoroutineScheduler> }`). So passing `runTest(testScheduler) { ... }` makes the testScope's testScheduler = the shared instance. Combined with `@BeforeTest { testScheduler = TestCoroutineScheduler(); Dispatchers.setMain(StandardTestDispatcher(testScheduler)) }` + `@AfterTest { Dispatchers.resetMain() }`, this shares the testScheduler between viewModelScope's Main dispatcher (set via setMain) and runTest's testScope. Drain, advance time, and lifecycle all operate on the same scheduler.
- **`runCurrent()` + `advanceTimeBy(t)` + `runCurrent()` drain pattern, NOT `advanceUntilIdle()`** (new this session, in `NotificationBadgeViewModelTest.kt:62-77, 79-103, 105-131`): viewModelScope coroutines are NOT tagged `BackgroundWork` (only `TestScope.backgroundScope`-launched coroutines get that tag, per `TestCoroutineScheduler.kt:69` `val isForeground = context[BackgroundWork] === null`). So `delay(REFRESH_INTERVAL_MS)` scheduled from the poll loop is a FOREGROUND event. `advanceUntilIdle` runs events while `events.none(TestDispatchEvent::isForeground)` returns false — which is never for a poll loop (each iteration schedules another foreground delay). `advanceUntilIdle` loops forever in real time. `runCurrent()` runs only events with `time <= currentTime` (per `TestCoroutineScheduler.kt:127-136`) — doesn't advance time. `advanceTimeBy(t)` advances to targetTime + processes events with `targetTime > event.time` (strict inequality, per `TestCoroutineScheduler.kt:158-180`) — the delay-at-exactly-`targetTime` resume isn't auto-processed; the follow-up `runCurrent()` drains the now-due resume + the inner launch it schedules. Strict inequality is why `advanceTimeBy(60_000)` alone isn't enough — the poll loop's `delay(60_000L)` resume is scheduled at exactly +60_000ms virtual time (delta from `currentTime` which starts at 0). After `advanceTimeBy(60_000)`, `currentTime = 60_000`, but the event at `time=60_000` is NOT processed by advanceTimeBy's `targetTime > event.time` check (60_000 > 60_000 → false). `runCurrent` then drains it because `it.time <= timeMark` (60_000 ≤ 60_000 → true). The poll loop's next iteration's delay is scheduled at +120_000 — outside runCurrent's range. So the pattern reliably advances exactly one iteration: `advanceTimeBy(interval_ms); runCurrent()`. For "dispose cancels loop" assertion: `vm.dispose()` cancels `viewModelScope` → delay's continuation cancellation disposes the event from the scheduler queue; `advanceTimeBy(180_000); runCurrent()` finds the queue empty → counter unchanged.
- **`vm.dispose()` AT END OF EACH TEST BODY before `runTest`'s internal post-body drain** (new this session, in `NotificationBadgeViewModelTest.kt:76, 102, [implicit in 117-dispose test]`): critical for Android JVM unit tests. `runTest` (per `TestBuilders.kt:370`) calls `testScheduler.advanceUntilIdleOr { false }` to drain remaining events after the testBody returns. The condition `{ false }` means "don't halt early" — runs until queue empty. With viewModelScope's poll loop still active (pending `delay(REFRESH_INTERVAL_MS)` foreground event), the drain resumes the CL{last-due delay}, which schedules another iteration (which would `viewModelScope.launch` → `Dispatchers.Main.immediate` access). After `@AfterTest { Dispatchers.resetMain() }` has torn down Main (because @AfterTest runs AFTER the test method completes which completes after `runTest` returns — wait, the @AfterTest ordering vs runTest's internal drain is what matters here). The actual ordering pain: `runTest { ... }` block's `try { testBody() } finally { testBodyFinished.value = true; ... }` (per `TestBuilders.kt:317-319`) followed by `scope.cleanupTestCoroutines()` + `advanceUntilIdleOr { false }` — these run BEFORE `runTest` returns. So `runTest`'s drain is INSIDE the test method's call. `@AfterTest` runs AFTER the test method returns. So `resetMain` is called AFTER `runTest`'s drain. That should work — Main is still set during drain. Hmm — that contradicts the Android failure. Re-reading: the Android failure was because of the OLDER pattern (setMain/resetMain INSIDE test body's `try { ... } finally { ... }`), not the @AfterTest pattern. The @BeforeTest/@AfterTest pattern (this session's resolution) lets Main stay set during drain — but drain itself loops forever for the poll loop. So `vm.dispose()` is still needed to halt the drain. Without `vm.dispose()` AND with @BeforeTest/@AfterTest setup, drain loops forever in real time (advancing virtual time through every poll iteration). With `vm.dispose()` called in the test body BEFORE return, the poll loop's pending delay is cancelled, queue is empty, drain returns immediately. **Decision**: every poll-loop VM test must call `vm.dispose()` before the test body returns, REGARDLESS of where setMain/resetMain live. Documented in `NotificationBadgeViewModelTest.kt` class-level KDoc lines 27-42.
